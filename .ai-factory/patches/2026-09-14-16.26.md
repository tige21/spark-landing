# Печатня в hero читалась как «по середине»: выравнивали картинку, а не рисунок

**Date:** 2026-09-14 16:28
**Files:** src/components/hero/HeroScroll.css, tests/layout.spec.ts
**Severity:** medium

## Problem

Гравюра с печатней в hero стояла ровно по центру страницы и налезала на
заголовок, вместо того чтобы держать правую половину. Пара «текст + печатня»
не читалась как единый блок и была смещена влево.

Замер по скриншоту 1512×900 (контентная ширина 1501):

```
левый край копирайта          190px от края
правый край краски печатни   1152px  → правое поле 349px
```

Поля 190 / 349 — блок завален влево на 159px.

## Root Cause

`.hero-bg` выравнивался по сетке правильно: `right: <container content edge>`,
внутри `object-fit: contain; object-position: right center`. То есть на линию
сетки клали **правый край КАРТИНКИ**.

Но у самой гравюры внутри кадра есть поле чистой бумаги справа. Замер всех 55
кадров `public/hero-frames/hero/*.webp` (960×852):

```
0001: ink x 90→800   right margin 159px (16.6%)
0014: ink x 60→800   right margin 159px
0028: ink x 12→802   right margin 157px
0042: ink x 15→790   right margin 169px
0055: ink x 12→798   right margin 161px
```

Краска кончается на x≈800 из 960 — стабильно на всей последовательности.
160/960 = **шестая часть собственной ширины кадра** уходит в пустую бумагу.

При `contain` по высоте (renderedH = 100svh = 900, renderedW = 1014) это
1014 × 160/960 = **169px**, на которые видимая печатня не доходила до линии
сетки. Отсюда и ощущение «стоит посередине»: картинка на сетке, рисунок — нет.

## Solution

`--hero-art-nudge` — величина этого поля бумаги в единицах вёрстки; коробка
`.hero-bg` выдвигается вправо ровно на неё:

```css
--hero-art-nudge: min(
  calc(100svh * 160 / 852),              /* contain по высоте: все реальные десктопы */
  calc((100vw - var(--hero-inset)) / 5)  /* contain по ширине: высокое узкое окно */
);
.hero-bg { right: calc(var(--hero-inset) - var(--hero-art-nudge)); }
```

160/852 берётся от отрисованной ВЫСОТЫ, потому что renderedW = renderedH ×
960/852, и `renderedW × 160/960 = renderedH × 160/852`. Второй член выведен из
`shift = 0.1667 × boxW`, где `boxW = 100vw − inset + shift` → `shift = 0.2 ×
(100vw − inset)`; на границе режимов оба выражения совпадают, поэтому `min()`
переключается без скачка.

За правый край вьюпорта уезжает только пустая бумага — краска всегда встаёт
ровно на линию сетки.

Попутно `--hero-inset` вынесен в переменную: одно и то же выражение
`max(--space-xl, (100vw − --maxw)/2 + --space-xl)` было продублировано в
`.hero-bg` и в `.hero-content`.

Результат — Δ(левое поле − правое поле) = 0 на 761/800/900/1024/1280/1440/
1512/1920/2560px. Пиксельная проверка скриншота: 190 / 191.

## Prevention

- **Выравнивая иллюстрацию по сетке, выравнивай КРАСКУ, а не рамку файла.**
  У любой сканированной/сгенерированной гравюры есть собственные поля; `contain`
  + `object-position` кладут на сетку край файла. Померить bbox краски в
  исходнике — три строки на PIL, и сразу видно, сколько это в процентах.
- **Мерить поля бумаги по ВСЕЙ последовательности, а не по первому кадру.**
  Здесь правый край краски оказался стабилен (798–802 из 960), и только поэтому
  константу можно зашить. Если бы он гулял, компенсация дышала бы вместе со
  скрабом.
- **Компенсацию, зависящую от `object-fit: contain`, писать через `min()` двух
  режимов.** Одна формула верна только пока `contain` упирается в ту же сторону;
  вторая покрывает противоположный случай, а на границе они равны.
- **Тест должен проверять инвариант дизайна, а не текущее число.** Старый тест
  утверждал `bgRight === grid line` — он проходил и в сломанном виде, потому что
  на сетке была рамка. Новый считает край краски из геометрии кадра и проверяет
  равенство полей пары; без правки падает.
