# Cert-mismatch on sparkcards.space after premature origin decommission during DNS cutover

**Date:** 2026-06-14 04:32
**Files:** infra — old server 185.214.108.29 (nginx vhost + LE cert + webroot for sparkcards.space)
**Severity:** high (live site showed "connection not secure" + a stranger's login to real visitors)

## Problem

After migrating the landing to a Russian VPS (83.217.215.66) and switching reg.ru DNS,
visitors on phones/networks that still had the **old IP cached** (TTL was 6h) opened
https://sparkcards.space and got iOS/Chrome "Это подключение не защищено / This connection
is not secure", then a prompt to log into an unrelated account.

## Root Cause

I decommissioned the **old origin too early** — removed the sparkcards.space nginx vhost,
its Let's Encrypt cert, and webroot from 185.214.108.29 right after the DNS change, while
public resolvers were still serving the old A record (6-hour TTL). Clients still resolving to
the old IP then matched the old server's **default server block** (an unrelated `claude-office`
service), which presented a cert for `claude-office-tige.duckdns.org` → SNI/cert-name mismatch
warning, and the claude-office app's login screen. A self-test from the new server to its own
public IP returned the correct cert, which masked the issue (loopback hit local nginx; the
breakage only affected external clients still pinned to the old IP).

## Solution

Restored the landing on the old server as a **bridge**: copied the still-valid LE cert
(live + archive + options-ssl-nginx.conf + ssl-dhparams.pem) back from the new server, replaced
the certbot-built `sparkcards.space` vhost (443 + redirect), recreated `/var/www/sparkcards.space`,
rsynced `dist/`, reloaded nginx. Verified server-side (`openssl s_client -servername
sparkcards.space` → `CN=sparkcards.space`) and externally (check-host: 200 from RU + global nodes;
RU TCP reach to the new server ~2 ms). Both origins now serve identical content; the old one will
be decommissioned only **after** DNS has fully propagated past the old TTL.

## Prevention

- **Never decommission the old origin during a DNS cutover until propagation completes.** Keep BOTH
  origins serving identical content for at least the old record's TTL (here 6h), ideally verify the
  old origin is receiving ~no traffic first.
- **Lower the DNS TTL (e.g. 300s) BEFORE a planned migration**, then raise it after — so cutovers
  drain in minutes, not hours.
- A green self-test from the origin to itself is **not** proof for external clients — verify from an
  independent external vantage point (check-host.net, mobile on cellular) and explicitly test the
  *old* IP path during a cutover.
- Decommission checklist: (1) DNS changed, (2) wait > old TTL, (3) confirm old origin idle, (4) only
  then remove vhost/cert/webroot.
